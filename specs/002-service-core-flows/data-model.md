# Phase 1 — Data model: Service core flows

**Feature**: `002-service-core-flows` | **Date**: 2026-08-25

Two models are described here and they are deliberately different objects: the **domain
model** (`domain/model`, framework-free, per `docs/service/code_rules.md` § 1) and the
**persistence model** (`adapter/out/persistence`, JPA-annotated). They are mapped by hand.

## 1. Domain model (`domain/model`)

### 1.1 `ValidationRequest` — entity

| Attribute | Type | Notes |
|---|---|---|
| `id` | `UUID` | Identity. Assigned at creation. Serialized as `requestId`. |
| `document` | `DocumentMetadata` | Owned value object, immutable, never `null`. The reference is replaced exactly once, when processing records the discovered size. |
| `status` | `ValidationStatus` | Current state. Only changed by the transition methods below. |
| `result` | `ValidationResult` | `null` until `complete(...)` is called. |

Mutable class, no public setters. Behavior:

| Method | Precondition | Effect |
|---|---|---|
| `static create(DocumentMetadata)` | — | New id, status `PENDING_UPLOAD`, no result. |
| `static restore(UUID, DocumentMetadata, ValidationStatus, ValidationResult)` | — | Public static rehydration used only by the persistence mapper (which lives in another package); performs no transition and runs no guard. |
| `confirmUpload()` | any | `PENDING_UPLOAD → QUEUED`; from any other status it is a **silent no-op** (idempotent confirm, `docs/business-rules.md` § 6). |
| `startProcessing()` | status is `QUEUED` | `QUEUED → PROCESSING`; otherwise throws `InvalidStatusTransitionException`. |
| `complete(ValidationResult)` | status is `PROCESSING` | `PROCESSING → COMPLETED`, stores the result; otherwise throws. |
| `fail()` | status is `PROCESSING` | `PROCESSING → FAILED`; otherwise throws. |
| `recordDiscoveredSize(long)` | — | Replaces `document` with a copy carrying the size storage reported. The only mutation of `document` after creation, and the reason the field is not `final` (approved amendment to `docs/service/code_rules.md` § 1). Not a setter: it is a transition method of the aggregate, callable only during processing. |

### 1.2 `DocumentMetadata` — value object (`record`)

| Field | Type | Rules |
|---|---|---|
| `filename` | `String` | Required at creation (`@NotBlank` at the web boundary). |
| `contentType` | `String` | Required, non-blank MIME string at creation. Whether it is *supported* is a processing-time rule, not a creation-time one. |
| `sizeInBytes` | `long` | `0` at creation. Set once, during processing, from what storage reports. |
| `storageKey` | `String` | Generated by the service at creation; never client-supplied. |

### 1.3 `ValidationResult` — value object (`record`)

| Field | Type | Rules |
|---|---|---|
| `verdict` | `Verdict` (`PASS` \| `FAIL`) | Never `null` when a result exists. |
| `fields` | `Map<String, Object>` | Stubbed extraction output; currently `{"filename": <filename>}`. |
| `reason` | `String` | Non-null for every `FAIL`; `null` for `PASS`. |

### 1.4 `ValidationStatus` — enum

`PENDING_UPLOAD`, `QUEUED`, `PROCESSING`, `COMPLETED`, `FAILED`.

```
PENDING_UPLOAD ──confirmUpload()──► QUEUED ──startProcessing()──► PROCESSING ──complete()──► COMPLETED
                                                                             └──fail()─────► FAILED
```

One-directional. No transition returns to an earlier status. `confirmUpload()` from a
non-`PENDING_UPLOAD` status is a no-op, not an error; every other invalid transition throws.

### 1.5 `PresignedUpload` — value object (`record`)

| Field | Type | Notes |
|---|---|---|
| `url` | `String` | The signed `PUT` URL returned to the client. |

Returned by `DocumentStoragePort.createPresignedUpload(...)`. Lives in `domain/model` so the
port signature stays framework-free.

### 1.6 Domain exceptions

Plain `RuntimeException` subclasses in `domain/model`, no Spring types:

| Exception | Thrown when | Mapped to |
|---|---|---|
| `ValidationRequestNotFoundException` | `findById` finds nothing | `404` Problem Details |
| `InvalidStatusTransitionException` | an illegal transition is attempted | `409` Problem Details |
| `DocumentStorageException` | the storage backend fails (not "object missing") | `502` Problem Details; during processing it drives the request to `FAILED` |

### 1.7 Named constants

Per FR-032, in the class that owns the rule (the processing use case):
`SUPPORTED_CONTENT_TYPE = "application/pdf"`, `MAX_DOCUMENT_SIZE_BYTES = 15L * 1024 * 1024`,
`MIN_DOCUMENT_SIZE_BYTES_EXCLUSIVE = 0`, and the three reason strings
`UNSUPPORTED_CONTENT_TYPE_REASON`, `EMPTY_FILE_REASON`, `FILE_TOO_LARGE_REASON`.

## 2. Persistence model (`adapter/out/persistence`)

One table. The idempotency key is an attribute of the request (R-001), not a record of its own.

### 2.1 Table `validation_request`

| Column | Type (Liquibase) | Constraints | Maps to |
|---|---|---|---|
| `id` | `uuid` | PK, not null | `ValidationRequest.id` |
| `status` | `varchar(32)` | not null | `ValidationRequest.status` (enum name) |
| `filename` | `varchar(255)` | not null | `document.filename` |
| `content_type` | `varchar(255)` | not null | `document.contentType` |
| `size_in_bytes` | `bigint` | not null, default `0` | `document.sizeInBytes` — `0` until processing records the discovered size |
| `storage_key` | `varchar(512)` | not null | `document.storageKey` |
| `result_verdict` | `varchar(16)` | nullable | `result.verdict` (enum name) |
| `result_fields` | `varchar(4000)` | nullable | `result.fields`, serialized as JSON text (R-002). `clob` was the first choice, but Liquibase resolves it to `text` on PostgreSQL and `CLOB` on H2 and no single Hibernate mapping validates against both under `ddl-auto: validate`; `varchar` is identical on the two. The stubbed payload is a single filename, far under the limit. |
| `result_reason` | `varchar(512)` | nullable | `result.reason` |
| `idempotency_key` | `varchar(255)` | nullable, unique index | the key the request was created with |

Indexes:

| Name | Columns | Kind | Why |
|---|---|---|---|
| `pk_validation_request` | `id` | primary key | identity |
| `ux_validation_request_idempotency_key` | `idempotency_key` | unique | enforces FR-024 in the database; multiple `NULL`s remain allowed |

No `version` column (R-004). No audit timestamps — nothing in the spec or the docs reads them.

Table naming is namespaced to the domain (`validation_*`) per
`docs/service/architecture.md` § 4.5.

### 2.2 Liquibase

`db/changelog/db.changelog-master.yaml` (today an empty list) includes one changelog per
change; this feature adds `db/changelog/changes/001-create-validation-request.yaml`
containing the `createTable` and the `createIndex` above, plus an explicit `rollback` for the
table. Types are restricted to the portable set (`uuid`, `varchar`, `bigint`) so the
same changesets run on PostgreSQL and on H2 in PostgreSQL mode, and the entities validate against
both (R-003).

### 2.3 Mapping

`ValidationRequestMapper` (package-private, static methods) maps field by field, both
directions — no MapStruct, per `docs/service/code_rules.md` § 3. It is the only place that
serializes/deserializes `result_fields` and the only place that rehydrates a
`ValidationRequest` without running its transitions.

## 3. Message model (`adapter/out/messaging`)

### 3.1 `ProcessingRequestedEvent` — `record`

| Field | Type | Notes |
|---|---|---|
| `validationRequestId` | `UUID` | The only field. Thin event: the consumer re-reads the request from the database. |

Topic `validation.processing-requested`, key = `validationRequestId.toString()`, JSON
serialization, consumer group `validation-service` — all already fixed by
`docs/service/kafka.md`. This record lives in the messaging adapter and never crosses into
`domain` or `application`.

## 4. Application-layer input/output records (`application`)

Reused directly as the HTTP request/response shapes — there is no separate DTO layer
(`docs/service/code_rules.md` § 6).

| Record | Fields | Used as |
|---|---|---|
| `CreateValidationCommand` | `filename` (`@NotBlank`), `contentType` (`@NotBlank`) | create request body |
| `CreateValidationResult` | `requestId`, `status`, `uploadUrl` | create response body |
| `ConfirmUploadResult` | `requestId`, `status` | confirm response body (R-005) |

The read endpoint returns the `ValidationRequest` domain object itself, Jackson-annotated at
the web boundary (the one accepted exception to domain purity), exposing `requestId`,
`status` and `result`; `document` is not serialized.
